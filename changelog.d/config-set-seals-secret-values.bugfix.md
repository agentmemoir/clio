`clio config set` now seals a value on disk whenever the value itself carries a secret, not only when the config path is one Clio stores sealed. Setting an endpoint such as `extract.url`, `embed.url`, or `rerank.url` to a URL with userinfo credentials used to print the value as `[REDACTED]` while writing the password into the deployment config file in the clear; the file now holds the same sealed envelope any other secret gets, and the value reads back unchanged. A password that contains `@` is recognized as a password, because the userinfo runs to the last `@` of the authority.

A saved envelope is opened on load only at a path where a save would have sealed it, judged on the plaintext it holds, so the sealed value at an ordinary path reads back normally and the existing refusal of a plaintext secret at a path Clio stores sealed is unchanged. Two consequences matter. A plain value that happens to begin with the envelope prefix is read back as the text it is, rather than refusing the whole file. An envelope moved to a path the save would not seal stays the opaque sealed text instead of being handed back as readable plaintext.
