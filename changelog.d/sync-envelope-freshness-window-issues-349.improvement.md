A new operator setting, `sync.max_envelope_skew_secs`, refuses a pulled or pushed sync envelope whose sealed `transaction_time` sits more than the given number of seconds behind the applying node's clock, so a node that never journaled a mutation id can no longer apply that mutation's replay. It defaults to `0`, which turns the age check off and leaves every envelope eligible, because a wall-clock bound cannot tell a replay from a legitimate backlog — a node that was offline for longer than the window — and refusing that backlog loses the write. Set it to a window comfortably larger than your longest expected offline period, or leave it off. `CLIO_SYNC_MAX_ENVELOPE_SKEW_SECS` overlays the setting from the environment, and the past bound is the only direction it tunes.
A separate fixed allowance of one hour refuses a stamp further ahead of this node's clock, so a fast clock cannot win every later merge, and the past bound of `0` disables that check too. Comparing a stamp means converting the UTC transaction stamps clio-sync writes to Unix epoch seconds, so both bounds read one clock. A refused row takes the `Stale` outcome: it is never applied and never journaled, both routes quarantine it under `stale_envelope`, or `malformed_stamp` for a stamp this build cannot place, the pull path advances its cursor past it, the serve push route reports it rejected instead of accepted, and `clio sync status` shows a per-bank `stale_refused` count and the last refusal line.
