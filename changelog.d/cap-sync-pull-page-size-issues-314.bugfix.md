The sync server now caps the page size a pull may request at the pull page limit. Before this change a peer could send an oversized `limit`, and the server read and serialized that many journal rows in one response. A peer with a valid token could exhaust server memory and stall other clients. A pull asking for more than the limit now receives one bounded page and resumes from the returned cursor; a pull asking for zero rows receives one row so the client advances instead of repeating an empty page.
A pull page is also bounded by a serialized byte budget, not only by a row count. The row cap alone could still let one page carry gigabytes when a row holds a large sealed payload; the server now stops assembling the page before the budget and always keeps one row, so the client advances and resumes from the cursor.
