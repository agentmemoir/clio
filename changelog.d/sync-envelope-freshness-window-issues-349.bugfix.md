Sync apply now keeps an ordering mark per device and per entity kind, and refuses an envelope whose stamp is strictly below the newest stamp already applied from that device for that kind. Such an envelope is refused without consulting the mutation-id journal, so a replay is caught even when the journal no longer holds the original mutation. The device identity that keys the mark is stored once per installation and read back on every open, so the mark survives a restart; an explicit environment override sets the identity per node when several nodes must report as distinct devices.

A stamp equal to the mark is accepted. Stamps have one-second granularity, so two real mutations from one device can carry the same stamp, and refusing an equal stamp would dead-letter real traffic. An exact repeat of that stamp is still caught by the mutation-id journal.

A refused envelope is recorded as a dead letter with reason `stale_envelope`, so an operator sees it in the pull acknowledgement instead of a silent duplicate that looks already applied.

Both wall-clock bounds are configuration keys under `sync` and both ship disabled at `0` seconds: `sync.freshness_max_age_secs` for the past age and `sync.freshness_max_future_secs` for a stamp ahead of the current time. Each key takes a whole number of seconds, zero or more, up to one hundred years; `0` turns that side off and nothing else. The past bound is off because a legitimate backlog can be arbitrarily old. The future bound is off because some entity kinds stamp the envelope with a valid time or a transaction time rather than the change time, so a legitimate row can carry a stamp in the future. A deployment whose stamps are known to be change times can set either key.
